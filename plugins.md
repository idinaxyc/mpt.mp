# Плагины mpt.mp

> **Статус: API v1, хост реализован в ядре** (`src/plugins.rs`, страница PLUGINS).
> Установки из GitHub-реестра в приложении пока нет — плагины кладутся в папку вручную (см. §2).
> LAN-сервер и синхронизация удалены из ядра; синхронизация должна быть отдельным плагином.
> Плагин можно проверять без плеера через `tools/mpt_plugin_host.py` — он ведёт себя как ядро.

## 1. Идея

Ядро остаётся маленьким: библиотека, плеер, очередь, `.m3u`/`.zip`. Всё остальное
(синхронизация, тексты песен, скробблинг, «сейчас играет» для панелей статуса, таймер сна…)
живёт в плагинах.

Плагин — **отдельный процесс**, который общается с ядром строками JSON через
stdin/stdout. Поэтому:

- плагин можно написать на чём угодно: Python, Rust, Go, Bash, Node;
- пока плагин выключен, он ничего не стоит: ни памяти, ни процессора;
- падение плагина не роняет плеер;
- плагины изолированы от зависимостей ядра; каждая функция-плагин сама выбирает свой стек.

Плагин **не рисует интерфейс сам**. Он описывает настройки и команды в манифесте,
а ядро показывает их в окне настроек (страница PLUGINS) и в строке статуса.
Благодаря этому плагины выглядят одинаково с любой темой и не тянут GUI-библиотек.

## 2. Быстрый старт

Нужен только Python 3.8+ (для тестового хоста; сам плагин может быть на любом языке).

```bash
# 1. Проверить готовый пример
python3 tools/mpt_plugin_host.py plugins/now-playing-file
python3 tools/mpt_plugin_host.py plugins/sleep-timer --set minutes=0

# 2. Свой плагин: скопировать пример и править
cp -r plugins/now-playing-file my-plugin
$EDITOR my-plugin/plugin.json my-plugin/main.py
python3 tools/mpt_plugin_host.py my-plugin      # код выхода 0 = нарушений протокола нет
```

Хост запускает плагин как ядро, отправляет `hello`, ждёт `ready`, прогоняет сценарий
(смена трека, пауза, `config_changed`, команды из манифеста, неизвестное событие),
отвечает на запросы заглушками и шлёт `shutdown`. Он ругается, если:

- в stdout попало что-то кроме JSON-сообщений;
- плагин не прислал `ready` за 5 секунд или не завершился за 3 секунды после `shutdown`;
- манифест некорректен или плагин подписался на событие без нужного права;
- плагин упал на неизвестном событии.

Папка пользовательских плагинов: `~/mpt.mp/plugins/<id>/`. Чтобы поставить плагин
вручную, положите туда папку с `plugin.json` в корне.

## 3. Структура плагина

```
<id>/
├── plugin.json     # манифест (обязателен)
├── main.py         # то, что запускается (или бинарник)
└── README.md       # что делает, какие права и зачем
```

Манифест — JSON, а не TOML: ядру не нужен ещё один парсер.

```json
{
  "id": "now-playing-file",
  "name": "Now Playing File",
  "version": "0.1.0",
  "api": 1,
  "description": "Пишет текущий трек в текстовый файл.",
  "author": "имя",
  "license": "MIT",
  "homepage": "https://github.com/owner/mpt-now-playing-file",
  "permissions": ["player.read"],
  "run": { "command": ["python3", "main.py"] },
  "settings": [
    { "key": "output", "type": "path", "label": "Файл", "default": "~/.cache/mpt-now-playing.txt" }
  ],
  "commands": [
    { "name": "sync_now", "label": "Синхронизировать" }
  ]
}
```

| Поле | Обязательно | Описание |
|---|---|---|
| `id` | да | `^[a-z0-9][a-z0-9-]{1,31}$`; совпадает с именем папки |
| `name`, `version` | да | `version` — `MAJOR.MINOR.PATCH` |
| `api` | да | версия протокола, сейчас `1` |
| `description`, `author`, `license`, `homepage` | нет | показываются в списке плагинов |
| `permissions` | нет | какие возможности ядра нужны (см. §5.4); по умолчанию пусто |
| `run.command` | да | команда запуска; рабочая папка — папка плагина; первый элемент либо программа из `PATH` (`python3`), либо файл внутри папки плагина (`./bin/plugin`) |
| `settings` | нет | настройки, которые ядро нарисует само |
| `commands` | нет | кнопки, нажатие приходит плагину как сообщение `command` |

Типы настроек: `string`, `bool`, `int` (необязательные `min`, `max`), `choice`
(обязателен `options: [...]`), `path`. У каждой есть `key`, `label`, `default`.
Значения приходят плагину в `config` (в `hello`) и обновляются событием `config_changed`.
Ядро **не** раскрывает `~` — это делает плагин (`os.path.expanduser`).

## 4. Жизненный цикл

1. Ядро запускает плагин при старте, если он включён, с переменными окружения
   `MPT_API`, `MPT_PLUGIN_ID`, `MPT_PLUGIN_DIR`, `MPT_DATA_DIR`
   (`~/mpt.mp/plugin-data/<id>/` — **только сюда** можно писать данные).
2. Ядро шлёт `hello`. В течение **5 секунд** плагин отвечает `ready`.
3. Дальше идёт обмен сообщениями. Плагин получает только те события, на которые
   подписался в `ready`, и на которые у него есть право.
4. При выключении плагина или закрытии плеера ядро шлёт `shutdown`.
   Плагин должен выйти в течение **3 секунд**, иначе его убьют (`SIGKILL`).
5. Если плагин упал сам, ядро перезапускает его до 3 раз с паузой 1, 5, 25 секунд,
   потом оставляет выключенным и пишет причину в журнал и строку статуса.

## 5. Протокол

### 5.1 Формат

По **одному JSON-объекту на строку**, UTF-8, `\n` в конце, не длиннее 1 МиБ.
У каждого объекта есть поле `type`. **Игнорируйте неизвестные `type`, события и поля** —
так API сможет расти без поломки старых плагинов.

В **stdout** — только сообщения протокола. Логи — в **stderr** (ядро сохранит их в журнал)
или сообщением `log`. Не забывайте `flush` после каждой строки.

### 5.2 Ядро → плагин

| `type` | Поля | Когда |
|---|---|---|
| `hello` | `api`, `core_version`, `plugin_id`, `data_dir`, `config`, `permissions` | сразу после запуска |
| `event` | `name`, `data` | подписка + право (см. 5.4) |
| `response` | `id`, `ok`, `result` или `error` | ответ на `request` |
| `command` | `name`, `args` | пользователь нажал кнопку из `commands` |
| `shutdown` | — | пора завершаться |

События:

| `name` | `data` | Право |
|---|---|---|
| `track_changed` | `{"track": Track, "index": 3}`; `track` — `null`, если очередь пуста | `player.read` |
| `state` | `{"playing", "position_ms", "duration_ms", "volume", "repeat", "shuffle", "queue_index", "queue_len"}` | `player.read` |
| `queue_changed` | `{"track_ids": [...], "index": 0}` | `player.read` |
| `library_changed` | `{"tracks": 1234, "playlists": 5}` — число, не сами данные | `library.read` |
| `config_changed` | `{"config": {...}}` — приходит всегда, подписка не нужна | — |

`state` ядро шлёт при смене `playing`/трека/перемотке и не чаще раза в секунду
во время воспроизведения. `repeat` — `"off"`, `"all"` или `"one"`; `volume` — 0.0…1.0.

Плагин, ставший готовым (`ready`) уже во время игры, сразу получает текущие `queue_changed`,
`track_changed` и `state` (если подписан): ядро досылает их при ближайшем такте. Остальным плагинам
при этом приходит повтор — события это уведомления, обрабатывайте их идемпотентно.

`Track` совпадает со структурой `model::Track` в ядре:
`{"id", "path", "title", "artist", "album", "duration_ms", "size"}`.
`id` — стабильный идентификатор трека в **этой** библиотеке; на другом устройстве он
другой, для сопоставления между устройствами используйте пару «имя файла + размер».

### 5.3 Плагин → ядро

| `type` | Поля | Смысл |
|---|---|---|
| `ready` | `subscribe: ["state", ...]` | готов; обязательно первым сообщением |
| `request` | `id`, `method`, `params` | вызов ядра; `id` — целое, уникальное в рамках процесса |
| `status` | `text`, `level` (`info`/`warn`/`error`) | короткая строка в карточке плагина и строке статуса |
| `log` | `msg`, `level` | строка в журнал |

Ответ ядра: `{"type":"response","id":7,"ok":true,"result":{...}}` или
`{"type":"response","id":7,"ok":false,"error":{"code":"permission_denied","message":"..."}}`.
Коды ошибок: `permission_denied`, `unknown_method`, `invalid_params`, `not_found`, `busy`, `internal`.
Ответы могут приходить вперемешку с событиями — сопоставляйте по `id`.
Ограничение: не больше 50 запросов в секунду, лишние получат `busy`.

Методы:

| Метод | `params` | `result` | Право |
|---|---|---|---|
| `player.get_state` | — | как у события `state` | `player.read` |
| `player.get_queue` | — | `{"track_ids": [...], "index": 0}` | `player.read` |
| `player.play` / `pause` / `toggle` / `next` / `prev` | — | `{}` | `player.control` |
| `player.seek` | `{"position_ms": 30000}` | `{}` | `player.control` |
| `player.set_volume` | `{"volume": 0.5}` | `{}` | `player.control` |
| `player.play_queue` | `{"track_ids": [...], "start": 0}` | `{}`; `not_found`, если ни один id не известен | `player.control` |
| `library.get_tracks` | `{"offset": 0, "limit": 200}` | `{"total": N, "tracks": [Track]}` | `library.read` |
| `library.get_track` | `{"id": "..."}` | `Track` | `library.read` |
| `library.get_playlists` | — | `{"playlists": [{"id","name","track_ids"}]}` | `library.read` |
| `library.create_playlist` | `{"name": "...", "track_ids": [...]}` | `{"id": "..."}` | `library.write` |
| `library.add_to_playlist` | `{"id": "...", "track_ids": [...]}` | `{}` | `library.write` |
| `library.rescan` | — | `{}`; если скан уже идёт, просьба запоминается и выполняется сразу после него | `library.write` |
| `library.get_folders` | — | `{"folders": ["/home/u/Music"]}` | `library.read` |
| `library.add_folder` | `{"path": "..."}` (`~` в начале раскрывается) | `{}`; `not_found`, если папки нет; повторное добавление той же папки — не ошибка | `library.write` |
| `settings.get_theme` | — | `{"name": "...", "colors": {"accent": "#a7c080", ...}}` | `settings.read` |
| `settings.set_theme` | `{"name": "...", "colors": {"accent": "#rrggbb"}}` — любые из 11 ключей файла темы | `{}`; `invalid_params` при неверном ключе или цвете | `settings.write` |

Эти методы соответствуют тому, что ядро уже умеет: `Player::play_queue/toggle/next/prev/seek/set_volume`,
`LibraryState::playlists`, `library::scan`.

Подробности:

- `player.play_queue`: `start` — позиция в **присланном** списке. Неизвестные ядру `track_ids` из очереди
  выпадают, играть начнёт первый известный трек начиная с `start`. Файл, который не открылся, не
  останавливает очередь: при переходе к следующему такой трек пропускается.
- `settings.set_theme`: повторная установка той же палитры ничего не меняет и не пишет на диск.
  За один сеанс принимается не больше 512 **разных** смен палитры (`invalid_params`); дальше нужен
  перезапуск плеера. Файл темы-симлинк не переписывается.
- Ядро сохраняет библиотеку и настройки с небольшой задержкой (доли секунды после последней правки),
  а при закрытии плеера дописывает всё, что не записано; ответ на запрос не ждёт записи на диск.

### 5.4 Права

| Право | Что даёт |
|---|---|
| `player.read` | события `state`, `track_changed`, `queue_changed`; `player.get_state/get_queue` |
| `player.control` | управление воспроизведением |
| `library.read` | событие `library_changed`; чтение треков и плейлистов |
| `library.write` | создание/изменение плейлистов, пересканирование, добавление папки в библиотеку |
| `settings.read` | чтение темы |
| `settings.write` | смена темы (меняется на лету и сохраняется в `~/mpt.mp/theme.toml`, если это не симлинк) |

`status`, `log` и `config_changed` доступны всегда. Просите **минимум**: пользователь
увидит список прав при установке.

## 6. Установка из GitHub

Нужна ровно одна точка входа — репозиторий-реестр (`<org>` выберите сами),
например `https://github.com/<org>/mpt-plugins`, в нём файл `index.json`:

```json
{
  "schema": 1,
  "plugins": [
    {
      "id": "now-playing-file",
      "name": "Now Playing File",
      "description": "Пишет текущий трек в текстовый файл.",
      "author": "имя",
      "repo": "owner/mpt-now-playing-file",
      "version": "0.1.0",
      "api": 1,
      "permissions": ["player.read"],
      "download": "https://github.com/owner/mpt-now-playing-file/releases/download/v0.1.0/now-playing-file-0.1.0.zip",
      "sha256": "64 шестнадцатеричных символа"
    }
  ]
}
```

Сам плагин лежит в **своём** репозитории; релиз — это GitHub Release с одним
zip-архивом `<id>-<version>.zip`, где `plugin.json` лежит **в корне архива**.

Ядро читает индекс с `raw.githubusercontent.com` и качает zip по ссылке из релиза —
это обычные HTTPS-запросы без GitHub API, поэтому лимит API (60 запросов в час без токена)
не мешает. Поиск плагинов через API по теме репозитория не используется: он лимитирован
и не проверен человеком.

Установка, шаг за шагом:

1. Скачать `index.json`, показать список (имя, описание, версия, права).
2. Пользователь выбирает плагин и **подтверждает права**.
3. Скачать `download`. Разрешены только `https://github.com/...` и редирект на
   `*.githubusercontent.com` (туда GitHub перенаправляет скачивание релизов). Размер — не больше 50 МиБ.
4. Посчитать SHA-256 и сравнить с `sha256` из индекса. Не совпало — отказ.
5. Распаковать во временную папку. Отказ, если путь в архиве абсолютный или содержит `..`
   (zip-slip), если нет `plugin.json` в корне, если `id`/`version`/`permissions` в нём
   не совпадают с индексом, если `api` не поддерживается.
6. Выдать `+x` только файлу, указанному первым в `run.command`, если он внутри папки плагина.
7. Переместить в `~/mpt.mp/plugins/<id>/` (старую версию — в `<id>.old/` на случай отката),
   записать `enabled: false` и дождаться, пока пользователь включит.

Обновление — тот же путь. Если у новой версии права **шире**, пользователь подтверждает заново;
автообновления без согласия нет.

## 7. Публикация плагина

1. Репозиторий с `plugin.json`, кодом и `README.md` (что делает, права и зачем).
2. `python3 tools/mpt_plugin_host.py .` возвращает 0.
3. Тег `vX.Y.Z`, zip `<id>-X.Y.Z.zip` с `plugin.json` в корне:
   `cd my-plugin && zip -r ../my-plugin-0.1.0.zip . -x '.git/*'`.
4. Приложить zip к GitHub Release, посчитать `sha256sum my-plugin-0.1.0.zip`.
5. Pull request в реестр: новая запись в `index.json`. Проверяющий читает код и сверяет
   права с тем, что плагин реально использует.

Проверку из п. 2 удобно повесить на CI (пример для GitHub Actions; не проверен, поправьте под себя):

```yaml
name: check
on: [push, pull_request]
jobs:
  host:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python3 tools/mpt_plugin_host.py .
```

## 8. Безопасность — что это даёт и чего не даёт

Плагин — это **программа, запущенная от вашего пользователя**. Права из манифеста
ограничивают только то, что плагин может просить **у ядра**. Они не мешают ему читать
ваши файлы или ходить в сеть: песочницы нет. Поэтому:

- ставьте плагины только из реестра или от тех, кому доверяете, и читайте код;
- sha256 в реестре защищает от подмены архива после ревью, но не от плохого кода внутри;
- обновления не ставятся без вашего согласия;
- разработчикам: не просите лишних прав, не отправляйте данные наружу без явной
  настройки, не пишите вне `MPT_DATA_DIR`.

Возможные усиления на будущее: подпись релизов (minisign), запуск через `bwrap`/Landlock
с отдельным флагом в манифесте. Сейчас в спецификацию они не входят.

## 9. Для ИИ-агентов

Если вас просят написать плагин для mpt.mp: прочитайте этот файл целиком, затем
посмотрите `plugins/now-playing-file/` (события) и `plugins/sleep-timer/` (команды и запросы).

Шаблон запроса человека к агенту:

```text
Напиши плагин для плеера mpt.mp по документу plugins.md.
Задача: <что должен делать плагин>.
Язык: <Python / Rust / ...>. Зависимости: только стандартная библиотека, если не сказано иное.
Сделай plugin.json, код и README.md. Права — минимально необходимые.
Проверь командой: python3 tools/mpt_plugin_host.py <папка плагина> — код выхода должен быть 0.
```

Правила, которые агент обязан соблюдать:

1. stdout — только JSON-сообщения, по одному на строку; после каждой строки `flush`.
2. Первое сообщение плагина — `ready` (после того как прочитан `hello`).
3. Логи и отладка — в stderr или сообщением `log`.
4. На `shutdown` выйти с кодом 0 за 3 секунды; фоновые потоки — daemon или остановить.
5. Неизвестные `type`, события и поля игнорировать, а не падать.
6. Каждый `request` — с уникальным целым `id`; ответ искать по `id`, не по порядку.
7. Подписываться только на нужные события и запрашивать только нужные права.
8. Данные писать только в `MPT_DATA_DIR` (или в путь из настройки пользователя), файлы — атомарно (`tmp` + `rename`).
9. `~` в путях раскрывать самим; рабочая папка плагина — его собственная папка, она может быть только для чтения.
10. Если из нескольких потоков пишете в stdout — защитите запись замком (пример в `sleep-timer`).
11. Не печатать секреты в `log` и `status`.

Типичные ошибки (хост поймает большую часть): `print` без `flush` → ядро ничего не получает;
отладочный `print` в stdout → нарушение протокола; плагин ждёт ответа на `request`, блокируя чтение
`stdin`, и пропускает события; подписка на событие без права → события не приходят; падение на
`KeyError`, когда `track` равен `null`.

## 10. Версионирование API

`api` — целое число. Добавление событий, методов и необязательных полей **не** меняет
версию (поэтому плагины обязаны игнорировать незнакомое). Несовместимое изменение — `api: 2`;
ядро будет поддерживать предыдущую версию в течение нескольких релизов и покажет у
устаревшего плагина предупреждение.

## 11. Как устроен хост в ядре

- **`src/plugins.rs`** — манифест и его проверка, запуск процессов, протокол, права, лимиты,
  перезапуски (1/5/25 с), `shutdown` с ожиданием 3 с. Три потока на процесс: чтение stdout,
  чтение stderr, запись в stdin (зависший плагин не замораживает интерфейс).
- **`src/engine.rs`** — запросы `player.*`/`library.*`, события, права, настройки плагинов:
  всё без привязки к GUI. Интерфейс (`src/iced_ui/`) забирает сообщения плагинов по таймеру
  (`Core::pump`) и рисует страницу PLUGINS.
- **`settings.rs`**: `plugins: { id: { enabled, granted, config } }`. `granted` — права, которые
  пользователь подтвердил, включая плагин; если плагин после обновления просит больше, он не
  запустится, пока его не включат заново.
- События считаются только когда есть хотя бы один готовый плагин — иначе ноль накладных расходов.
  Когда плагин сообщает `ready`, ядро досылает всем подписанным текущие `queue_changed`,
  `track_changed` и `state`; текущее состояние можно и запросить через `player.get_state`.
- За один такт интерфейса (250 мс, пока есть готовые плагины) обрабатывается не больше 256 сообщений
  плагинов, остальные ждут следующего: болтливый плагин не заморозит окно.
- Объект `Track` содержит ещё поле `mtime` (секунды Unix) — игнорируйте его.
- На Windows команда `python3` заменяется на `python`.
- Папки `<id>.old`, `<id>.tmp` и начинающиеся с точки пропускаются при сканировании.
- Не реализовано: установка из реестра (§6), проверка обновлений, песочница.

**LAN-синхронизация** — плагин `plugins/lan-sync` (подробности в его README): поднимает HTTP-сервер
только в своём процессе и только когда задан токен; запросы подписаны HMAC-SHA256 общего токена
(сам токен по сети не передаётся), в ответ тоже подпись. Принятые файлы пишутся в папку библиотеки
(`mpt-sync`) или в выбранную пользователем. Сетевой сервер в ядро не возвращается.
